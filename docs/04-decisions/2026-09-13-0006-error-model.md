# 0006: Error model

**English** | [Chinese](../zh-CN/04-decisions/2026-09-13-0006-error-model.md)

- Status: accepted
- Date: 2026-09-13
- Related: [Error model](../01-architecture/12-error-model.md)

## Context

[Fact] API failures need URL/status/headers/body diagnostics and retry classification for transient HTTP/connection failures; tool errors usually return to the model.

[Fact] Thiserror is standard for library errors; Clippy warns above 128-byte Result errors, requiring boxed rich payloads or a raised threshold.

## Decision

1. Use non_exhaustive `ProviderError` wrapping concrete errors and core `Error` wrapping provider plus core-specific variants.
2. Keep `ToolError` separate and nonfatal, converting it to model feedback.
3. Expose is_retryable, is_cancelled, status_code, and kind.
4. Project streaming failures into serializable `StreamErrorInfo`.
5. Keep `Error` at most 128 bytes by boxing large fields.

## Rationale

- Rust types replace Symbol markers and permit exhaustive matching.
- Structured URL/status/body/usage eliminates parsing diagnostic strings.
- Small errors reduce `Result` movement costs.

## Alternatives

- `Box<dyn Error>` alone loses structured matching.
- Unaggregated module errors complicate callers.

## Consequences

- New errors require variants and kind mappings.
- [Fact] PV-013 measured boxed `Error` at 56 bytes versus 360 inline; retain the ≤128-byte static assertion from `verification/pv013-error-size`.
